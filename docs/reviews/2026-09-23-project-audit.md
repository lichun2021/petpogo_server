# 全项目代码审核：安全性、冗余、耦合结构

审核日期：2026-09-23。范围为当前工作区，扫描 app/server 文件与 173 个路由文件，重点追踪认证、设备权限、积分、计划、签到、上传、回调、外部服务和部署。不是仅审查 GLB 改造，也不是线上渗透测试或逐行形式化验证。没有读取生产数据库或修改业务代码。

优先级：P1 应优先修复，P2 为明确的功能/维护问题。以下定位相对于仓库根目录。

## 安全性

### 1. [P1] 统一初始密码允许登录尚未自主设置密码的用户

位置：server/routes/sdkapi/auth/login-pwd.post.ts:33；server/routes/sdkapi/auth/login.post.ts:66。
短信注册直接写入统一初始密码的 MD5；密码登录又将空密码解释为相同初始密码。能够发送合法 App 请求且知道手机号的调用者，可在用户未改密码时通过本地密码验证，无需该用户短信验证码。本地替身测试确认空密码账号接受统一密码并进入对方账号登录阶段；没有访问真实账号。

建议：未设置密码时禁用密码登录，必须通过短信验证后设置个人密码。迁移已有默认密码账号；采用带盐的慢速密码哈希，不能仅把统一默认密码换成另一个值。

### 2. [P1] 请求签名不覆盖 nonce、路径或正文，防重放可绕过

位置：server/middleware/signature.ts:35；server/middleware/openapi-auth.ts:35。
App 签名只包含时间戳与密钥，Redis 去重的 nonce 不在签名内。本地测试中，同一签名换 nonce、换路径后仍被接受。OpenAPI 也只签 API Key 和时间戳，没有请求去重；掌握一组有效签名的人可在窗口内重复使用、改变请求内容。App 私有接口仍需用户 token，这不是单独绕过全部用户认证。

建议：版本化升级为 HMAC，覆盖方法、规范化路径/查询、正文摘要、时间戳和 nonce；OpenAPI 同样处理。消费等写接口另加业务幂等，签名防重放不能替代业务幂等。

### 3. [P1] App 可将自己的宠物关联到不属于自己的设备

位置：server/routes/sdkapi/pet/[id].put.ts:31；server/routes/sdkapi/pet/[id]/action.get.ts:18；server/routes/sdkapi/pet/fence/create.post.ts:8。
档案更新验证宠物归属，却直接写入客户端 deviceId，没有验证设                                                                                                                                                                                                                                                                                                         备访问权。硬件动作读取又把这个 device_id 当成可信关联读取设备缓存/事件。因此拥有合法账号且知道其他设备 ID 的调用者，可以污染本地关联，并读取目标设备近期动作（有有效上报时）。围栏创建同样缺少设备权限校验。不能据此断言所有设备功能均可被越权。

建议：统一设备访问检查，区分拥有、共享和只读权限；禁止档案更新充当未经验证的绑定入口。对方设备权限应按既有 Peer/AI access 机制验证，避免只依赖可能滞后的本地绑定表。

### 4. [P1] 积分扣减行锁未处于同一事务，存在并发超额消费

位置：server/utils/points.ts:317。
spendPoints 使用连接池逐句 query，未获取专用连接或开启事务。SELECT FOR UPDATE 无法保护后续更新；两个请求可以读取同一余额后各自按旧值覆盖。模拟并发数据库测试：初始 100，两个消费 80 的调用均成功，余额为 20，而流水累计消费 160。中途异常也可能仅扣部分批次或缺流水。

建议：专用连接+事务覆盖读取、锁定、全部扣减与流水；金额必须验证为有限合法数值；用并发集成测试验证。

### 5. [P1] AI 消费回调没有业务幂等，正常重试也会重复扣款

位置：server/routes/openapi/ai/consumption.post.ts:39；server/utils/points.ts:347。
refId 只是写进流水，没有唯一约束或已处理检查。调用方收到超时后重试同一消费事件，会再次扣款，即使修复签名也存在。

建议：消费事件 ID 必填，以来源+事件 ID 建唯一键；事件登记、扣款与结果落库同事务，重试返回第一次结果。按事件幂等，不要仅给可能拆成多个批次的流水 ref_id 加简单唯一键。

### 6. [P1，条件性] 生产凭证缺失时回退到源码中的固定值

位置：nuxt.config.ts:71；server/plugins/bootstrapAdmin.ts:13。
配置包含固定 JWT、App 签名及外部服务密钥的后备值，初始化管理员也允许使用固定默认密码。是否影响当前线上取决于环境变量，本次没有读取线上密钥或核实实际启用情况。

建议：生产缺少关键密钥时启动失败；删除真实凭证型默认值。曾投入使用的源码密钥应轮换；报告不复述其内容。

## 冗余与行为分叉

### 7. [P2] 日期计算多处复制，签到写入与领奖使用不同日期

位置：server/routes/sdkapi/checkin/signin.post.ts:5；server/routes/sdkapi/checkin/claim.post.ts:20；server/routes/sdkapi/checkin/status.get.ts:7。
签到按进程本地日期写入，领奖/状态按 toISOString 的 UTC 日期查询。进程运行于北京时间时，00:00–07:59 会出现当日签到已写入但领奖查询前一天的情况。补签和积分到期也存在本地日期/UTC 字符串混用。

建议：定义明确的 Asia/Shanghai 业务日工具，由签到、领奖、补签、周期发放统一使用，补充跨午夜和月末用例。

### 8. [P1] 周期积分存在两套独立发放实现，没有共同的幂等边界

位置：server/utils/points.ts:108、166、218。
ensurePeriodGrant 与 grantScheduledPoints 都执行“检查时间→插入积分批次→更新 last_grant_at”，没有锁定用户或唯一周期标识。用户访问与 cron 并发，或两个请求同时到期时，可重复发同周期积分。这是已经影响账务的重复逻辑，不只是代码行数问题。

建议：两条入口只负责找候选用户，共用一个带事务与周期唯一键的单用户发放服务。

## 耦合与事务边界

### 9. [P1] 业务状态与权益发放不在一个事务，失败后无法正常重试

位置：server/routes/sdkapi/checkin/claim.post.ts:48；server/routes/api/admin/plans/orders/[id]/confirm.put.ts:13；server/utils/plan.ts:75。
领奖先提交领取记录，再发积分；若发放失败，重试被“已领取”挡住。订单先标记已支付，再开通计划；失败时订单已支付而权益可能未生效。并发确认订单也没有条件更新或锁定，可能重复发权益。下层工具自行 useDb，导致上层难以统领事务。

建议：业务服务显式接收事务连接，状态变更和权益写入共同提交；非数据库外部通知使用提交后事件/可重试任务，不能放在长事务里。

### 10. [P2] 全局 fetch 拦截器用字符串包含判断认证范围

位置：app/plugins/adminAuthInterceptor.client.ts:8、21。
只要 URL 包含 /api/admin/ 就附加 token，没有验证同源；全局任何非登录请求返回 401 都清除管理员会话。后台已有通过 $fetch 上传到外部 OSS 的调用，认证逻辑与外部请求发生不必要耦合。未发现当前存在可由普通用户直接控制该目标 URL 的完整利用链，因此不将其报告为已证实的 token 窃取漏洞。

建议：独立 useAdminApi，限制同源且 pathname 以 /api/admin/ 开头；只有该客户端的 401 才清会话。外部上传使用独立客户端。

### 11. [P2] 部署不检查数据库版本，缺表会在上线后才暴露

位置：deploy.sh:85、101、125；server/utils/petModelAssignment.ts:12。
部署只打包应用并重启，未包含升级脚本或检查 schema 版本。新路由立即依赖新增表和字段，用户之前提供的缺表日志就是这一问题的实例。不能只靠 Nuxt 构建成功判断可上线。

建议：记录数据库 schema 版本，部署前执行幂等迁移或至少做版本检查；检查失败停止切换。迁移和代码发布需要兼容顺序，不建议在每次业务请求中自动建表。

### 12. [P2] 测试未接入统一检查入口，当前测试与实现发生漂移

位置：package.json:6；tests/peer-local-sync.test.mjs:31；tests/pet-model-assignment-api.test.mjs:17；tests/pet-model-assignment.test.mjs:10。
本次运行五个无需网络的测试文件，共 29 项：23 通过，6 失败。失败涉及旧数据库替身未支持配置查询、旧 GLB 配置缺少猫狗默认字段等。说明当前工作区不能沿用之前的“全部通过”结论；这些失败也不等于六个线上功能故障。package.json 没有 test/typecheck 检查入口。

建议：更新测试契约，把匹配、认证、资金幂等、并发和时间边界测试接入 CI；减少依赖 SQL 字符串形状的 mock，为账务使用真实临时数据库事务测试。

## 验证与边界

- 已运行：security-audit、pet-model-assignment、pet-model-assignment-api、peer-local-sync、admin-pet-resources 五个测试文件，29 项结果如上。
- 额外本地模拟复现：默认密码接受、签名换 nonce/路径复用、并发积分扣减不一致。模拟使用虚构账号与临时数据，没有发送真实登录/消费请求。
- 本次没有修改业务代码、部署、连接线上数据库或执行迁移；没有进行依赖漏洞数据库扫描、真实 OSS 权限检查、Nginx 配置验证或完整浏览器回归。
- 已有正向措施包括后台 JWT+Redis 会话与账号状态检查、App 用户状态校验、许多查询使用参数化 SQL、AI/Peer 固定上游与部分权限/响应大小检查、GLB 快照事务。这些措施不能抵消上述具体问题。

建议顺序：先处理账号默认密码和设备访问权；随后签名与消费幂等、积分及权益事务；再统一日期/周期发放服务；最后补齐发布与测试门禁，并渐进拆分业务服务。无需为此直接拆成微服务。
