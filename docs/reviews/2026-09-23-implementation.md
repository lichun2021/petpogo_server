# 全项目修复实施与上线说明

本次修改仅在本地代码和隔离测试库完成，未发布线上、未修改真实用户数据。原审核报告记录的是修改前结果，本文件记录修复后的行为。

后续业务调整：新注册账号恢复初始密码 `123456`，使用独立盐 scrypt 保存，可正常密码登录和以旧密码验证改密。下文“短信注册不设置密码”为首次安全改造记录，已被本次调整取代。已执行的 001 迁移不修改，历史空密码账号不自动批量恢复。此调整只需发布应用，不需要新的数据库迁移。

## 已完成

- 默认密码登录被拒绝；短信注册不设置密码；个人历史 MD5 登录成功后升级为异步 scrypt。密码字段迁移到 VARCHAR(255)。
- 改密支持旧个人密码，或 password_reset 用途短信验证码；验证码在 Redis 中原子验证和消费。改密增加 credential_version，旧本地 token 和绑定旧版本的 refresh 凭证失效。
- 旧默认/空密码账号的版本在迁移时首次递增，强制重新短信登录。新刷新接口只接受新登录登记过的 refresh 凭证，旧用户需重新登录一次。
- 宠物设备关联及围栏写入验证 Peer 所有者身份；动作读取验证设备访问权，核对设备 ID/MAC。共享用户目前只读，未知写权限默认拒绝。
- 所有积分写入口按用户锁串行，专用连接事务覆盖扣款/发放/流水；cron 与访问路径共用周期发放服务。
- AI 消费使用独立幂等操作表，相同事件重复调用返回首次结果，同 ID 改内容返回 409。订单状态与权益、领奖记录与积分同事务提交。
- 业务日期显式使用北京时间，数据库连接初始化会话时区；签到、状态、领奖、补签和日历使用同一业务日。
- App 和 OpenAPI 均支持签名 v2，使用原始正文缓存，代理不二次读取流。
- 删除源码固定凭证后备值，生产关键配置缺失时启动失败；初始化管理员要求显式密码。
- 后台请求包装只给同源后台接口附 token；外部 401 不再清后台会话。
- GLB 配置新增 revision 防止覆盖其他页面修改，资源校验仅锁定引用模型；保留猫/狗/未知类型默认和既有快照。
- 增加版本迁移、只读 readiness、统一测试与类型检查，部署改为独立发布目录及健康检查。

## 接口兼容变化：发布前必须联调

### 用户密码

`POST /sdkapi/auth/sms` 增加 `purpose`：默认 `login`，设置/重置密码用 `password_reset`。

登录后调用 `PUT /sdkapi/user/password`：

- 普通修改：`{ oldPassword, newPassword }`。
- 首次设置或重置：`{ code, newPassword }`，code 必须来自 password_reset 短信，登录用途短信不可复用。
- 新密码为 8–128 字符，拒绝常见默认值。
- 成功响应增加 `reLoginRequired: true`，客户端随后重新登录。

未设置个人密码的密码登录返回 403，`data.code=PASSWORD_SETUP_REQUIRED`。客户端应转短信登录。旧个人密码仍可验证并渐进升级；默认密码不会走兼容分支。

本地 session 失效不能撤销用户已经持有的 Peer 直连 token、AWS 凭证等。对方固定账号密码入口和跨系统 token 撤销仍需要对方后台配合，不把它们标记为已解决。

### AI 消费

`POST /openapi/ai/consumption` 现在必须提供稳定 `refId`，1–100 个字母、数字、点、下划线、冒号或短横线。同一业务消费的重试必须复用该 ID；不同消费必须使用不同 ID。

缺失 ID 返回 400；同 ID 改用户/类型/数量返回 409。余额不足的业务结果也被保存；之后充值不会让该事件的重试突然扣款，需要新业务事件。

source 固定来自此受认证服务端入口，不接受 body 指定来源。当前仍为单一 OpenAPI 调用方凭证，没有引入多租户调用方授权管理。

数量支持最多六位小数，最终金额必须精确为整数积分，范围 1–2147483647；拒绝隐式取整及 NaN/Infinity。计费规则未新增舍入约定，调用方如需要小数积分需另行定义精度并迁移数据库。

幂等记录不自动按 TTL 删除；查询结果中的余额为首次操作时结果，实时余额请另行查询。

### 签名 v2

Headers：`x-signature-version: 2`、`x-key-id: primary`、`x-timestamp`（13 位毫秒）、`x-nonce`（16–128 位字母数字下划线短横线）、`x-signature`（64 位小写 hex）。OpenAPI 仍额外携带 `x-api-key`。

HMAC-SHA256 密钥分别使用 APP_API_SECRET / OPENAPI_SECRET。签名字符串由以下内容按换行连接，末尾不追加换行：

1. `2`
2. `primary`
3. 大写 HTTP 方法
4. URL.pathname（保持 URL 解析后的转义表示）
5. URLSearchParams.sort() 后的查询字符串，同名参数保留顺序，按 URLSearchParams 规则编码
6. timestamp 原文
7. nonce 原文
8. 原始请求正文的 SHA-256 小写 hex（无正文为零字节摘要）

服务端入口使用实际可见的路径；代理不得在客户端签名后改写路径或正文。业务请求重试使用新 nonce，但消费 refId 不变。

`SIGNATURE_V2_REQUIRED=true` 强制 App v2；`OPENAPI_SIGNATURE_V2_REQUIRED=true` 强制 OpenAPI v2。

**这两个开关默认 false，方便调用方逐步迁移。旧 v1 的签名复用风险在兼容期仍存在，必须在联调完成后强制 v2 才算完成该项修复。** v2 验证失败不会回退 v1。当前仅支持 primary keyId，实际密钥轮换由运维协调，不宣称已提供多密钥自动轮换。

### 后台 GLB 配置

GET 返回 revision；PUT 必须带相同 revision，过期返回 409。升级后台与服务端应同步发布。猫狗保底仍需实际选择资源，迁移不猜测模型类型。

## 数据库与上线顺序

1. 确认 Node 至少支持 `--env-file` 和 process.loadEnvFile（建议与开发测试一致的维护中版本）；准备线上数据库备份，暂停周期任务及积分写入流量。
2. 检查生产 JWT_SECRET、APP_API_SECRET、OPENAPI_KEY、OPENAPI_SECRET 均显式配置。现有曾使用的源码密钥应轮换；腾讯 IM 等外部服务按实际使用配置。首次空管理员表还需至少 12 位 ADMIN_PASSWORD。
3. 空库先执行修正后的 sql/init.sql；已有库不要重跑 init.sql。两者随后均执行 `npm run db:migrate`，再执行 `npm run db:check`。
4. 迁移 `001-security-ledger.mjs` 会扩容密码、增加凭证版本与幂等表、补齐 GLB 字段及 revision，并为历史模型保存快照。不会补发历史积分或修改已有猫狗默认配置。
5. 完成 App 设置密码、AI refId 的联调后发布。`./deploy.sh --migrate` 会暂停旧 PM2 进程并升级，`./deploy.sh` 默认只检查 schema。外部 cron 的暂停需运维安排，脚本不会自动寻找并修改 crontab。
6. 部署在 releases 下准备独立目录，shared/.env 与应用包分离；通过只读健康检查后切换 current。首次运行沿用服务器原 .env；不上传本地 .env。运行包装将历史 MYSQL_* 等环境变量映射为 Nuxt 运行时覆盖；显式 NUXT_* 优先。
7. 确认健康与业务验证后恢复流量和周期任务。迁移后失败不能回退到默认密码/旧积分写逻辑，应使用仍兼容新 schema 的修复版本；不删除幂等记录或缩短密码列。

迁移工具持有数据库命名锁，每个已完成版本记录校验和；已执行迁移不可再修改。DDL 不保证事务回滚，因此迁移按可重复步骤设计，失败需诊断后续跑。此版本不自动修补历史账务差异；需单独对账确认后处理。

部署前数据库失败会阻止切换。迁移模式暂停旧进程后若失败会保持停止，不以恢复已知不安全的旧版本换取表面可用；恢复步骤必须事先演练。

原 start.sh/restart.sh 为旧布局运维脚本。新版本日常使用 `pm2 restart petpogo-server` 保留部署时注册的入口；不要重新用旧 ecosystem.config.js 注册进程。后续发布统一使用更新后的 deploy.sh。

## 验证方式

- `npm test`：纯逻辑、路由模拟、本地模拟上游测试；数据库集成测试未配置 socket 时明确跳过。
- `TEST_MYSQL_SOCKET=/path/to/isolated.sock npm test`：额外执行真实 MySQL 集成用例，测试建立并删除带测试前缀的独立库；仅对隔离实例运行，不能把生产 socket 传入。
- `npm run typecheck`：Nuxt 生成类型 + TypeScript 检查（尚不是 Vue 模板的完整 vue-tsc 检查）。
- `npm run build`：Nuxt 完整构建。
- `npm run check`：串联测试、类型、构建。真实 MySQL 集成验证需要 CI 显式提供测试 socket，不以跳过结果代替账务验收。

本次已在本机隔离 MySQL 8.4 验证初始化、迁移重复执行、并发扣款、同事件20次重试、故障回滚、cron/用户并发及订单重复确认。未在生产联调 App、短信供应商、Peer 权限、AWS 或 AI 消费上报。

最终本地结果：67 项测试全部通过，无跳过；TypeScript 检查、Nuxt 构建、部署脚本语法检查及 diff 空白检查通过。未进行生产发布和恢复演练。

## 与原建议的范围差异

- 周期发放采用既有 last_grant_at 持久化状态与用户行锁，在同一事务中推进；没有新增独立周期表。幂等消费事件使用独立唯一键，订单与领取继续使用各自状态和约束。
- 本轮已限制后台全局请求包装的凭证作用范围；逐页迁移 useAdminApi、进一步消除重复 authHeader 尚未完成。
- 已抽取事务、日期、凭证、资源权限和消费服务；没有对所有路由一次性拆分 repository，部分业务仍使用 Nuxt auto-import。完整 DTO 收敛和目录重组属于后续结构重构。
- 签名跨语言联调、真实 Redis 端到端验证码验证、历史账务对账、生产密钥轮换与恢复演练仍需完成，不将本地测试视为这些事项的验收。
