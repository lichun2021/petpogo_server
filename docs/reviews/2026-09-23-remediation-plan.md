# 全项目修改建议与执行方案

日期：2026-09-23。基于同目录 project-audit 审核报告及本次补充代码检查。
状态：已完成方案复核，尚未实施业务代码、数据库或线上配置修改。
范围：原审核 12 项问题，以及实施这些修复必需的密码字段、请求体读取、历史数据、初始化 SQL 和测试迁移。维持 Nuxt/Nitro 单体，不引入微服务或通用规则引擎。

## 1. 实施原则与优先级

1. 尽快封堵统一密码登录和未经授权的设备关联；这两项不等待整体重构完成。
2. 数据库先做兼容性扩展，再切换代码。修复账务时统一切换所有积分写入口，避免新旧写入逻辑并存。
3. 客户端协议升级与内部实现改造分开。旧签名、短信设置密码和第三方消费事件 ID 的迁移必须有明确期限，不能宣称兼容期间旧漏洞已消除。
4. 资金、权限、日期行为使用业务测试验收；不以代码更短、构建成功或 SQL mock 通过作为唯一标准。
5. 不自动清空历史密码、积分、订单或宠物关联。先生成只读核查结果，再执行可追踪的定向修复。
6. App 签名不是用户授权边界，包内共享密钥可能被提取；每个私有接口仍必须校验用户及资源权限。

## 2. 建议拆成七批交付

| 批次 | 内容 | 依赖 | 可验收结果 |
| --- | --- | --- | --- |
| A | 修复测试基线；建立迁移执行/校验入口；统一基础类型和业务日期工具 | 无 | 失败用例原因明确，空库和旧库升级可验证 |
| B | 禁用默认密码登录、修复设备关联及读取权限 | 与 A 并行推进 | 默认密码不能登录，不能引用他人设备 |
| C | 用户密码哈希迁移、短信设置/重置密码、安全配置校验 | A；与 App 协调设置密码入口 | 旧个人密码可渐进升级，新密码只用安全格式 |
| D | 积分事务、消费幂等、周期发放、签到领奖、订单权益 | A 的迁移和日期工具 | 并发不超扣、不重发，失败不留下半完成状态 |
| E | App/OpenAPI 签名 v2 和客户端切换 | 原始请求体共用实现；调用方完成联调 | 改路径/正文/nonce 均验签失败，重试不重复消费 |
| F | 后台 API 客户端、重复逻辑收敛、类型完善 | 相关领域修复稳定 | 外部请求不携带后台凭证，也不清后台会话 |
| G | 发布目录、健康检查、迁移门禁、恢复演练 | 各批次验收 | 迁移失败不切换；兼容版本可恢复服务 |

测试和迁移保护从 A 开始提供，不拖到 G 才补。时间取决于 App/第三方联调及历史数据状况，不给未经验证的工期承诺。

## 3. 安全性改造

### S1. 默认密码与个人密码迁移（对应审核 1）

修改范围：`server/routes/sdkapi/auth/login.post.ts`、`login-pwd.post.ts`、`server/routes/sdkapi/user/password.put.ts`、`server/utils/password.ts`、用户表迁移，以及登录/密码相关测试。

具体方案：

- 短信注册不再写统一密码；没有自主密码的用户不能使用密码登录，返回稳定业务码 `PASSWORD_SETUP_REQUIRED`。
- 空密码及现有统一默认密码的摘要一律要求短信验证。无法区分“系统默认”和“用户主动设为同一个弱密码”的历史记录，都需要重新设置。
- 保留非默认历史 MD5 的短期验证入口；验证成功后升级为带算法标识的安全哈希。格式识别必须严格，不能因解析失败回退为默认密码。
- 复用现有 scrypt 思路，增加异步实现和输入长度上限，避免在高并发 App 登录中使用同步高成本运算阻塞事件循环。保留已有管理员哈希的读取兼容，不另造第二套不兼容密码系统。
- 先将 `t_user.password VARCHAR(100)` 扩为 `VARCHAR(255)` 或更大经确认长度；当前管理员工具输出 32 位 salt + 分隔符 + 128 位摘要，共 161 字符，不能直接写入原字段。
- 设置/重置密码必须有“近期短信验证证明”，不能仅信任现有 token；已被默认密码登录获取的 token 不应具有设置账户凭证的能力。增加用途限定、短时有效、一次性消费的验证凭证，绑定用户/手机号和操作。
- 已设置密码的普通改密可校验旧个人密码；遗忘密码走短信证明。修改后按会话撤销策略使旧本地会话失效。
- 对方账号使用固定共享密码的现有约定需要单独核查：若公网允许凭账号直接登录，应由对方限制为可信服务端入口或提供受控换票机制；本地改成安全哈希不会自动修复这条直连信任边界。
- 明确本地 token 撤销不等于 Peer token、刷新凭证和直连硬件权限被撤销。需要对方提供撤销机制才能承诺跨系统退出；暂不具备时在发布方案中列明残余风险和过期窗口。

迁移顺序：字段扩容 → 发布新旧个人哈希兼容读取与默认密码拒绝 → 联调短信设置入口 → 渐进升级个人哈希 → 根据统计停止 MD5 兼容。不要回滚到仍接受默认密码的旧版本。

验收：默认摘要/空值均不能登录；正常历史个人密码首次登录只升级一次；长密码与无效格式受控拒绝；一次性短信证明不能跨用户、跨用途或重复使用；不能只靠既有 token 给空密码账号设密。

### S2. 设备与宠物授权（对应审核 3）

修改范围：宠物档案更新、硬件动作读取、围栏创建/读取、`server/integrations/ai/access.ts` 及 Peer 权限适配层。

- 抽取独立资源授权服务，API 明确区分 `deviceId`、MAC、`petId` 和所需能力（读取/关联/修改）。现有 `assertAiDeviceAccess` 按 MAC 检查，不能直接用数字设备 ID 调用。
- 服务端通过可信设备记录/Peer 返回结果解析 ID↔MAC，不信任客户端同时提交的映射。
- 本地宠物归属和设备权限分别检查；仅能访问宠物不意味着可引用任意设备。
- 档案更新未传 `deviceId` 时保留关联；明确解绑使用约定的 null；明确更换必须验证新设备权限。不要为了修复越权清掉所有历史关联。
- 读取硬件状态也验证权限，覆盖历史错误关联与共享撤销；上游不可用时不能默认为有权限。
- 先列能力矩阵：所有者可管理关联；共享用户的写能力以对方明确契约为准，不将“出现在设备列表中”直接解释为拥有全部写权限。
- 上游权限查询在数据库事务外完成；本地写入事务内锁定并复核本地归属/状态。跨系统撤权竞态不能靠本地事务消除，高敏感硬件写操作继续依靠上游最终授权。

验收：自己的设备、已接受共享、仅收到邀请、撤销共享、其他用户设备、ID/MAC 不匹配、上游超时均覆盖；不能通过旧错误关联读取其他设备状态。

### S3. 签名协议升级（对应审核 2）

修改范围：`signature.ts`、`openapi-auth.ts`、公共请求体读取、RedisKey、调用方协议文档和测试向量。

建议新增明确版本、keyId，采用 HMAC-SHA256。签名消息至少包含版本、keyId、HTTP 方法、规范化路径/查询、时间戳、nonce、原始请求体 SHA-256；App 私有请求可另绑定 token 摘要，禁止把原始 token 写入日志。

必须明确：

- 正文以接收的原始字节摘要为准，不把解析后的 JSON 再序列化；空正文、中文、空白、表单、重复查询参数、百分号编码均提供跨语言测试向量。
- 路径和查询规范化规则由服务端/App/第三方共同使用；请求压缩或代理重写若不支持，应明确拒绝或在边界统一处理。
- 正文只读取一次并缓存，统一限量与超时。现有 `readProxyBody` 直接消费请求流，新签名不能读完后让代理再次读取。对已缓存内容也执行适用的大小检查。
- 先校验长度、版本、时间戳、签名，再以 keyId+nonce 原子去重；nonce TTL 覆盖未来时间戳容差窗口。采用常量时间签名比较。
- 收到标注 v2 的失败请求绝不降级 v1；旧协议仅对明确允许的调用方/版本过渡开放，观察覆盖率后关闭，不能以客户端任意 header 自报版本绕过强制策略。
- App 内共享密钥不能替代用户 token 和资源授权；OpenAPI 的 keyId 对应服务端配置的调用方和可访问接口集合，不能让调用方自己指定身份。

验收：任何字段变更均拒绝；相同 nonce 并发仅一次通过；v2 验签失败不能降级；App 的合法重试使用新 nonce、同一个业务事件 ID。

### S4. 配置、密钥和日志（对应审核 6，补充防护）

修改范围：`nuxt.config.ts`、`jwt.ts`、`bootstrapAdmin.ts`、启动检查、部署说明及零散日志。

- 同时移除 runtimeConfig 和 `jwt.ts` 内的固定密钥兜底。生产关键凭证缺失时启动失败；可选外部功能关闭时不强制要求其凭证。
- 初始管理员凭证只用于管理员表为空时的显式初始化，不要求现有数据库每次启动仍保留初始化密码；也不能静默生成默认管理员。
- 安全配置校验独立于会捕获并吞掉初始化异常的 bootstrapAdmin；必须真实阻止 readiness/启动，不能只打印错误后继续提供服务。
- 检查仅报告“缺少哪个配置项”，不打印值。构建环境与实际运行环境分别验证，不能因本地构建时设置过就认定生产已设置。
- 已使用过的源码密钥需轮换；JWT、App/OpenAPI、腾讯 IM、Peer 会话的影响分别评估。旧新 keyId 的接受窗口由服务端控制，禁止无限保留旧密钥。
- 收敛业务路由中的原始回调、手机号和查询参数日志，使用请求摘要与业务事件 ID。仅验证 logger 插件脱敏不足以证明全部日志安全。
- X-Forwarded-For 的可信边界需核查 Nginx/网络配置；没有配置证据时，不声称限流无法绕过。

验收：必要密钥为空/占位值时启动失败；已有管理员不因缺初始化密码而无法启动；日志无密码、token、验证码和完整敏感回调；轮换前后有明确会话行为。

## 4. 积分、计划与签到改造

### D1. 明确账务事务边界（对应审核 4、9）

建立 `withTransaction`，事务内函数必须接收专用连接；禁止在事务函数内部重新 `useDb()` 获取池连接，也禁止隐藏嵌套事务。

建议拆为：

- points repository：只做 SQL 和行映射，所有 ID 保持字符串。
- points service：消费、发放、到期、余额；带事务版本清晰命名。
- entitlement service：订单确认/签到领奖，组织状态与积分原子变更。
- period grant service：统一周期发放，供 cron 和用户访问调用。

统一并发边界：同一用户的所有账务写操作先锁该用户的账户锁行（可复用用户行），再依固定顺序操作事件、订单/领奖记录和积分批次；多用户操作按稳定 ID 顺序锁定。没有积分批次时也必须有可锁定的用户级行。订单所属用户在拿锁后复查，不能仅相信事务外快照。

一个消费事务内完成：事件幂等检查 → 到期批次处理及有效余额读取 → 判断足额 → 按到期顺序扣减 → 写每个批次流水 → 保存消费结果 → 提交。任何异常整体回滚。为防遗漏更新，可加 `remaining >= take` 条件并校验 affectedRows，不能以该条件代替整个事务。

外部 HTTP、短信、IM 不放在账务事务中。必须可靠投递的外部动作使用同事务 outbox，再由重试任务发送；纯提示允许提交后发送。只对明确未提交的死锁/冲突进行有上限重试；提交结果不确定时按事件 ID 查询，不盲目重做。

余额读取和周期发放拆开：现有 getPointsBalance 会写库，迁移调用者时显式保留“先同步应发权益，再读取”的业务行为，避免拆分后漏发。

### D2. 消费事件幂等（对应审核 5）

建议新增 `t_points_operation`（最终 DDL 在实现时根据实际 schema 校核）：

| 字段 | 用途 |
| --- | --- |
| id | 内部操作 ID |
| source、event_id | 经鉴权的调用方来源与稳定外部事件 ID，唯一组合 |
| user_id、operation_type | 操作用户与消费/发放类别 |
| request_hash | 规范化业务入参摘要，检测同 ID 换内容 |
| amount、rule_snapshot | 最终扣款与当时计价规则快照 |
| status、result | 已完成/明确业务拒绝以及可重放的结果 |
| created_at | 审计时间 |

- source 从服务端认证结果取得。event_id 为大小写语义明确的字符串，使用匹配协议语义的二进制/大小写敏感排序规则；不能依赖默认不区分大小写的数据库 collation。
- 同 ID 同业务参数返回首次结果；同 ID 不同参数返回冲突，不额外扣款。请求摘要不包含会随重试改变的签名时间戳/nonce。
- 计价使用精确数值规则。现有批次/流水是 INT：必须明确 quantity 的单位、允许精度、上下限及最终取整方式，再实现为精确运算。不能悄悄把现有小数消费全部向上取整；这是发布前需业务确认的计费契约。
- 未执行的系统故障可重试；余额不足等已确认业务结果建议固定返回，不因稍后充值就在同一次请求重试中扣款。希望再次消费必须产生新事件，并明确调用方行为。
- 不给流水 ref_id 简单加唯一键，一次操作可能拆为多条批次流水；流水增加 operation_id 关联。
- 幂等记录不能按随意短 TTL 删除；保留期覆盖调用方最大重试/补报窗口，过期请求有明确拒绝策略。
- 旧调用方缺 refId 时无法可靠去重：不能用手机号+金额+时间猜事件。新增 v2 强制稳定 ID；v1 过渡若保留需明示残余风险，并约定截止日期。

验收：20 个同事件并发只扣一次；同事件不同用户/数量报冲突；100 分余额并发两个不同事件各消费 80，仅一次成功；断连后重试结果一致；多批次消费流水可完整对账。

### D3. 统一周期发放（对应审核 8）

cron 只扫描候选用户，最终是否到期必须在统一发放服务、用户锁内重新判断。定义持久化 grant cycle ID/period key，并有唯一约束。

周期标识基于持久化周期状态和订阅版本，不按每次调用的 now 临时生成。保留现有“离线不追溯多次，只发当前一次”的策略，除非业务明确变更。升级/续费引起的周期重置要有清晰边界，不能与旧计划补发混用。

用户到期判断、插入批次、流水和更新周期状态同事务。迁移先根据 last_grant_at 建立未来周期基线，不假造历史流水、不立即补发全部历史周期。

验收：cron 与登录/余额请求并发只发一次；重复扫描无新增；Free→付费、计划过期降级、无赠送额度、长期离线都符合约定。

### D4. 领奖与订单（对应审核 9）

- 领奖资格判断、唯一领取记录、积分批次、流水同事务；并发重复领取返回既有成功结果或稳定业务错误。补签修改 streak 的过程也按用户统一串行，避免边界竞态。
- 订单确认锁定用户和订单，验证状态，以订单 ID 作为权益事件标识；订单状态、订阅权益、赠送积分共同提交。不要继续用 planId 作为订单发放唯一来源。
- applyPlan 不得间接调用会自动 ensurePeriodGrant 的通用发放函数，否则切换计划时可能先补发一次新计划周期积分，再赠送一次。
- 明确同档续费剩余时长、升级/降级、生效日策略；本次安全修复不顺便更改计费产品规则。
- 历史“有领取记录无积分”“已支付无权益”先只读核对；现有流水不一定能唯一对应订单，不足以证明时不能全量自动补发。确认后以独立修复事件 ID 发放并保留审计。

验收：每个写入点注入失败都整体回滚；相同订单并发确认只生效一次；数据库提交后响应丢失，重试不会再发权益。

### D5. 日期与到期（对应审核 7）

建立显式 Asia/Shanghai 的业务日期模块。进程运行于 UTC 或 Asia/Shanghai 时，得到相同业务日；不要只封装依赖系统时区的 getFullYear/getDate。

分别表示业务 DATE 和绝对时刻。短期保留现有 MySQL DATETIME 的存储约定，统一写入格式；不要在此次修复中整体切换 UTC 存储。不得再把 toISOString 去掉 Z 后作为北京时间 DATETIME 写入。

MySQL 驱动的 timezone 选项不能替代数据库会话时区。核查并显式统一连接的 session time_zone，使 NOW()/CURDATE() 与业务日约定一致；连接池新建连接也必须应用。

日期校验必须确保 YYYY-MM-DD 真正存在，不能让 2 月 30 日自动滚动。签到、状态、领奖、补签、周期计算使用同一模块。已混用的历史日期不做全表机械平移，需要按数据来源核查。

验收：北京时间 23:59:59/00:00:00、07:59/08:00、月末、年末、闰年、不同进程 TZ；签到后状态和领奖始终读到同一天。

## 5. 冗余与模块结构

### R1. 前端后台请求客户端（对应审核 10）

新增 useAdminApi，只接收后台相对路径或明确的同源 URL，比较 URL.origin 与准确的 pathname 前缀。token 注入和 401 清理仅作用于后台认证请求；登录失败按登录页面处理。

逐页替换已有 authHeader 与全局包装。OSS 上传、第三方请求使用独立 fetch；迁移期旧包装也先收紧到同源后台接口，防止混用窗口继续扩大。不要增加“全局 fetch 会自动带凭证”的新调用。

验收：所有后台页面正常携带 token；外域 URL 即使含 /api/admin/ 也无 token；外部 401 不登出；后台认证 401 清本地会话一次。

### R2. 后端模块边界

逐步建立 auth、resourceAccess、points、entitlement、businessDate、petAppearance 六个领域边界。路由仅做输入解析/鉴权/服务调用/输出；SQL 放在各领域 repository。公共层只放被实际复用的工具，避免建立无类型的“万能 CRUD”。

Nuxt auto-import 保留在路由边缘；业务服务通过明确 import 和参数依赖连接、时钟、外部适配器，测试不再依赖大量 globalThis 注入。先改高风险业务，不为目录统一一次性搬动全部路由。

统一可复用内容：ID 字符串校验、整数分页、业务日期、事务封装、明确 DTO、分页输出、数据库 JSON 解码、权限检查、形象快照生成。GLB 预览与实际分配继续共用同一个匹配器。

### R3. GLB 与后台配置补强

保持猫、狗各自默认和未知类型保底；不改变已有宠物快照。调整测试以适配三个默认字段。

配置整体保存增加 revision/乐观锁，避免多个页面覆盖；模型校验按实际引用 ID 查询和加锁，避免锁定整个资源表。规则 JSON 通过类型/schema 验证；资源停用默认保护保持同一事务约束。快照是历史分配记录，不应因为“去冗余”删除。

未传字段保留、明确置空的语义统一制定；尤其宠物资料更新不能因未传字段清空设备、背景或其他资料。重新匹配属于显式操作，不在普通修改或重复同步中触发。

## 6. 数据库、发布和检查入口

### M1. 最小迁移机制（对应审核 11）

新增按版本排序的迁移目录、迁移记录表（版本、校验和、状态/完成时间）、单执行者锁。迁移只通过运维入口执行，不在业务请求里建表。

MySQL DDL 不承诺随业务事务整体回滚。每一步必须可检测、可续跑；成功后才记录完成，失败保留诊断状态并阻止应用切换。已执行版本的内容不再修改。

先确认运行库版本、字段、索引与表，不假设 init.sql 等于生产结构。空库 baseline 与已有库 upgrade 分开；已有库不能重复跑整份 init.sql 作为升级。

补充发现：当前 init.sql 在签到领取表结束处存在重复的表尾语句，需修复并用目标版本 MySQL 验证整个初始化脚本；还需验证脚本中条件 ALTER 等语法的实际兼容性，不能用 Nuxt 构建替代 SQL 验证。

建议扩展顺序：密码字段 → 幂等操作表/关联字段 → 周期状态 → 迁移版本记录和 readiness 检查。GLB 先核对现有 schema，再登记已完成升级，不能盲目重做或把未完成迁移标成功。

### M2. 发布与恢复

现有 deploy.sh 原地清理文件后再解压，建议改为独立 releases 目录：上传 → 校验包/配置 → 迁移检查 → 备用目录启动及健康检查 → 切换 → 重启或重载 → 业务探针。

应用包、外部配置和日志分开；配置不随清理目录删除，不把数据库备份放在会被部署清理的位置。固定构建产物及锁文件，生产安装失败必须准确返回失败。

readiness 验证必要配置、数据库版本和关键依赖；外部可选服务异常不等同于整个服务不可用。新实例健康检查不得消费短信、扣积分或创建真实订单。

账务代码切换前暂停新积分写入和周期任务、等待在途事务结束，再完成切换；不能让新旧账务版本同时写。恢复服务只回滚到仍兼容新 schema 且保留安全修复的版本，不删除账务事件或回退密码列长度。

### T1. 统一检查（对应审核 12）

增加 test、test:integration、typecheck、check 等明确入口；Nuxt 构建仍必须执行。Node 版本固定并与生产一致，不依赖某位开发者本地 Node 24 才支持的 TS 直接执行方式。

先修目前六项测试失败的 mock/配置契约，不通过删除断言取得绿灯。为账户、权限、签名、事务、幂等、日期增加真实业务测试。MySQL/Redis 集成测试使用隔离库，不复用生产连接。

CI 分层：纯逻辑测试 → 隔离数据库事务/故障测试 → Nuxt 类型与构建 → 新库初始化/旧库升级/重复执行 → 关键后台页面冒烟。依赖漏洞与密钥扫描可加入，但本次未执行过，不能写成已完成。

## 7. 发布前必须澄清的契约

这些问题不阻塞明确的默认密码拒绝、输入校验和越权修复，但阻塞相关最终发布：

| 问题 | 建议 | 未确认时处理 |
| --- | --- | --- |
| App 是否已有短信设置/重置密码入口 | 接入用途限定的一次性验证证明 | 保留短信登录，禁用默认密码，不伪造已验证状态 |
| 共享设备具体写权限 | 按 Peer 已确认的能力矩阵 | 未确认的写操作拒绝，不能从只读访问推导 |
| AI 数量单位与小数计价 | 明确精度、边界及取整 | 不改变价格规则；先拒绝 NaN/Infinity/非法负值 |
| 调用方是否能提供稳定消费事件 ID | v2 必填来源内唯一 ID | 明示旧接口无可靠幂等，约定停用窗口 |
| 签名 v1 停用日期 | 统计调用方覆盖后设置服务端截止 | 不宣称迁移窗口内已完全防重放 |
| Peer token/refreshToken 撤销能力 | 与对方确认退出、改密、封禁策略 | 只承诺本地会话撤销，列出直连残余风险 |
| 历史积分和订单如何补偿 | 只读对账后定向修复 | 不按模糊流水自动批量补发 |

## 8. 统一验收清单

- 原审核 12 项逐一有修复提交、回归用例和迁移/兼容说明。
- 默认密码禁用、跨用户设备访问阻断；所有私有接口仍校验用户权限。
- 同事件并发只生效一次，不同事件余额不足时不能超扣。
- cron 与请求并发只发一次；领奖、订单、积分提交与回滚一致。
- UTC 与北京时间进程下签到/领奖业务日一致。
- v2 签名跨语言向量一致，正文只读一次；旧协议退出有可执行安排。
- 新旧密码与字段扩容兼容，失败登录不升级，默认摘要不得走旧哈希兼容。
- 外部请求不接收后台 token，第三方 401 不清后台登录状态。
- 空库、旧库、部分迁移失败后的续跑均成功；重复迁移不重复加权益。
- 构建、类型检查、测试通过，部署前准备与恢复演练有记录。

详细的方案复核结论见同目录 `2026-09-23-remediation-review.md`。以上均为待实施建议，不代表生产风险已经消除。
