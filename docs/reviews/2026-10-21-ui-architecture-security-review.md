# 宠联芯后台 UI、架构与安全审查

审查日期：2026-10-21。基线：`d9e181d`。本轮仅审查，未修改应用代码、线上配置或业务数据。

## 结论与范围

后台已经有可保留的视觉基础：暖灰背景、橙色主色、统一字号、分组导航，以及 Nuxt UI 的按钮和弹窗。当前主要问题是各页独立实现导致的交互不一致、状态处理缺口和维护成本；不建议换框架或整体重写。

范围包括全部27个后台页面的结构与样式检索、代表页面源码阅读、174个路由的安全模式检索，以及鉴权、上游代理、上传、日志、部署链路重点审查。视觉实看包括登录、用户列表、音乐列表及上传弹窗；后台业务页面使用本地虚构数据代理，未登录线上后台。没有逐个执行174个接口，也没有操作真实设备。

验证：81项现有测试通过，5项真实MySQL集成测试因未提供测试环境跳过；类型检查与生产构建成功。这些检查不能替代以下未覆盖的业务与安全问题。

依赖检查使用 npm 官方 registry 的 `npm audit --omit=dev`。结果为42个受影响包条目：6 critical、27 high、6 moderate、3 low；不是42个独立且均可远程利用的生产漏洞。Nuxt将部分构建和开发工具纳入依赖链，需要分别核对开发环境与最终生产产物的可达性。

## 一、必须优先处理的代码发现

### S1 · P1：敏感配置随构建产物分发（已验证）

位置：`nuxt.config.ts:89-115`，`deploy.sh:80-91`。

`runtimeConfig` 默认值在构建阶段从 `process.env` 读取。Nuxt构建时加载本地 `.env` 后，这些值进入服务端产物；部署时不复制 `.env` 并不能阻止它们随 `.output/server` 分发。

在本轮新构建产物中确认出现本地 `MYSQL_PASS`、`JWT_SECRET`、`APP_API_SECRET`、`OPENAPI_SECRET`、`ALI_OSS_KEY_SECRET` 等配置值。验证只输出字段名，没有输出值。这是服务端产物包含秘密，不等于这些秘密已暴露在浏览器客户端。

建议：敏感项默认设为空，统一由运行时 `NUXT_*` 环境变量注入；现有 `scripts/start.mjs` 的旧变量映射可继续作为迁移入口。CI构建不带真实凭证，增加产物秘密检查；核对产物历史分发和访问范围后决定哪些凭证需要轮换。

验收：换一个无密钥构建环境仍可构建；启动依赖线上注入；产物扫描不再发现真实秘密。

### S2 · P1：设备告警回调的账号映射错误（源码确定）

位置：`server/routes/openapi/device-event/callback.post.ts:53-62`。

代码将手机号补成 `手机号@qq.com`，然后拿邮箱形式查询 `t_user.phone`。与此前刷新登录的错误相同：本地用户以纯手机号存储时，离线、围栏越界、低电告警会在查用户处404，无法继续落库和推送。

建议：集中维护本地手机号和Peer账号的转换，仅接受明确支持的格式；查询手机号列时使用规范手机号。补充裸手机号、邮箱账号、无效格式、未知账号的测试。不要对任意邮箱随意截取用户名。

### S3 · P1：OpenAPI旧签名可在时间窗内重复使用（默认兼容路径）

位置：`server/middleware/openapi-auth.ts:35-51`，`nuxt.config.ts` 的 `openapiSignatureV2Required`。

v1只签 `apiKey + timestamp + secret`，没有绑定请求方法、路径、正文，也没有nonce去重。知道一组有效签名的人在5分钟内可再次发送，并可将其用于其他路径或正文。代码已有v2，但默认不强制。实际线上是否仍接受v1需核对运行配置。

建议：为上游调用方制定迁移窗口，最终强制v2；每个合作方使用独立密钥和接口权限。扣费等接口已有业务幂等是优点，但动作上报、告警回调仍需稳定事件ID，避免重试造成重复落库和推送。

验收：相同nonce被拒绝；修改body/path/method后原签名失效；相同业务事件重投不产生第二条业务效果。

### S4 · P1：第三方账号共用固定密码，形成独立于本地鉴权的访问风险

位置：`server/utils/peerBackend.ts:168-179`，登录响应中的 `peer.gatewayUrl`。

所有Peer账号均由手机号推导，且密码固定。即使本地短信、封禁和凭证版本校验正确，只要Peer公网入口允许直接密码登录，攻击者就可能绕过本地鉴权访问设备侧数据。当前代码能确认统一密码设计，不能仅凭源码确认上游公网实际开放范围或其额外风控。

建议：优先与上游确认网络和登录策略；将账号服务限制为受信服务端访问，逐步改为服务端身份交换或每用户独立随机凭证。不要只修改本地密码校验而认为已解决上游边界问题。

### S5 · P1：锁定依赖命中高危公告，需要独立升级与回归

位置：`package-lock.json`。检查到的版本包括 Nuxt 4.4.4、@nuxt/devtools 3.2.4、Axios 1.15.2、Vue/SSR renderer 3.5.33。

npm审计返回多个critical/high条目，其中DevTools有未认证RPC命令执行公告。开发工具风险首先影响开发机；不能直接据此宣称生产服务可远程执行命令。

建议：为依赖升级单独建变更，检查官方修复版本、依赖链和实际调用点；开发服务只监听本机，不经公网反代；检查生产 `.output` 与部署安装是否引入非必需开发工具。不直接运行 `npm audit fix --force`。

参考：[DevTools安全公告](https://github.com/advisories/GHSA-279x-mwfv-vcqv)。

### S6 · P2：上传签名缺少完整的服务端边界

位置：`server/routes/sdkapi/upload/sign.post.ts:29-65`。

`folder`直接进入对象key；未知MIME会回退到扩展名；签名PUT未在此处绑定内容类型和大小，也未按用户划分目录。当前实现限制了谁能领签名，但没有在应用代码中完整限定实际上传内容与体积。OSS是否另有限额或策略未核验。

建议：业务目录使用枚举，key加入用户ID；拒绝不支持的MIME，按类型设置大小上限；使用OSS可强制的上传策略或上传后核验，并通过回调建立所有者记录。下载展示与管理后台使用隔离域名。

参考：[OWASP文件上传指南](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html)。

## 二、UI重点审查

### U1 · P2：加载失败与真实空数据混淆

位置：`app/pages/admin/stores/index.vue:105-114`，`app/pages/admin/index.vue:82-94`。

门店请求失败后直接替换为 `{list:[],total:0}`，页面显示“暂无门店”；首页吞掉错误后保留占位符和空列表。运营会误判为数据被清空，且没有有效的重试入口。设备列表已有明确失败状态，可作为统一方式。

修改：区分首次加载、成功有数据、成功空列表、筛选无结果、加载失败、后台刷新。失败时保留最后一次成功数据并标注未刷新；显示简洁原因、重试和requestId。

### U2 · P2：固定列宽与裁切容器组合导致窄屏操作不可达

位置：`app/pages/admin/music/index.vue:93-114`，用户与门店列表同样需统一检查。

音乐用固定宽度CSS grid模拟表格，外层是 `overflow-hidden`，没有横向滚动容器或窄屏替代布局。内容宽度不足时名称列被挤压，右侧操作可能被裁切。不是继续缩字号能解决的问题。

修改：桌面列表提供最小宽度和横向滚动，操作列固定；窄屏将次要信息折叠进详情。验收至少覆盖1280、1024、768、390宽度及浏览器200%缩放。

### U3 · P2：关闭标签未驱逐缓存，表单离开缺少统一保护

位置：`app/layouts/admin.vue:115-118`，`app/composables/useTabStore.ts:110-137`。

KeepAlive只设置固定max=15，关闭标签只移除tabs数据，未按打开标签约束缓存。用户“关闭”页面后，重开可能继续看到旧组件状态；大表单有未保存改动时，没有统一的离开处理。退出登录也未集中清理全局业务缓存。

修改：为路由缓存制定明确规则，关闭即驱逐对应实例；列表在需要时用onActivated刷新；表单使用dirty状态、离开提示与可选草稿；退出时清理管理员相关缓存。保留切换标签时的表单状态，但区分“切换”和“关闭”。

### U4 · P2：系统设置的批量保存缺少事务与并发版本

位置：`app/pages/admin/settings.vue:405-413`，`server/routes/api/admin/settings.put.ts:34-46`。

前端提交所有配置，服务端逐条更新，中途失败会形成部分保存；两个管理员同时编辑时，后保存的整批旧值还可能覆盖先保存的新值。该问题属于UI反馈与数据可靠性的共同缺口。

修改：前端仅提交修改项并展示变更摘要；服务端先校验后事务提交，增加revision冲突检查；冲突保留草稿并提示重新比对。保存期间禁止重复提交，加载失败时不显示可用的保存入口。

### U5 · P2：普通管理员看到无法执行的管理入口

位置：`app/layouts/admin.vue` 的navBase；`server/routes/api/admin/settings.put.ts:6`、`server/routes/api/admin/push.post.ts:4`、积分及计划写接口。

导航只对管理员管理做角色区分，系统设置、推送、积分和计划编辑入口对普通管理员仍可见，而相应写接口要求super_admin。API权限是有保护的，问题是界面允许编辑到最后才返回403。

修改：建立统一权限清单，页面支持明确的只读态，隐藏或禁用无权限操作并说明原因；服务端继续校验权限，不能只靠前端隐藏。

### U6 · 视觉建议：保留暖色品牌，统一信息主次和操作密度

本轮看到的后台不是“全面字号太小”：现有13/14/16/20/28px规格已经生效。主要视觉差异来自页面各自的表头、筛选、边框、状态样式和操作排列。

建议固定规范：

| 项目 | 统一规则 |
| --- | --- |
| 字体 | 13辅助、14正文、16区块标题、20页面标题、28统计；ID用等宽字体 |
| 间距 | 4/8/12/16/24/32；页面边距24、卡片内距16或24 |
| 颜色 | 橙色用于主操作及选中；正文深灰；绿色/红色仅表达业务状态 |
| 表格 | 表头44px、常规行56–64px；主名称14px，辅助字段13px；长文本可展开 |
| 按钮 | 常规36px高；每页一个主操作；删除放次级操作或菜单 |
| 弹窗 | 小表单约448px、普通表单640px、复杂资源编辑880px；正文滚动、底部操作固定 |
| 状态 | 同一种状态用同一Badge；不混用标签、边框框块与纯颜色表达 |
| 页面头 | 标题、简短说明、总数/更新时间、主操作放在固定区域 |

视觉上优先优化用户、设备、帖子、资源这四种页面模板，再迁移其余页面。音乐里emoji与Heroicons混用、门店空态直接要求“SQL导入”等内容也应统一；运营界面应给可执行的业务引导。

### U7 · 可访问性与键盘操作需要补齐

位置：`app/pages/admin/settings.vue:49-57` 等自绘开关；`app/layouts/admin.vue` 的右键菜单。

自绘开关只绑定click，没有完整的switch角色、aria-checked和名称；右键菜单也没有统一的键盘进入、焦点管理和Escape退出方案。部分筛选外观像Tab，但语义各自不同。

修改：优先复用已安装的Nuxt UI开关、菜单、表单字段组件。为纯图标操作提供清晰可访问名称，字段标签与input关联；错误文案关联到字段，而非只弹toast。

## 三、耦合与框架扩展

### A1 · 页面同时承担接口、表单、上传、弹窗与样式职责

27个页面合计约6916行，存在172处内联style。音乐667行、电子宠物环境535行、反馈465行。行数本身不是缺陷，但这些页面同时维护多种独立业务状态，修改上传或错误处理时容易漏页。

建议按业务拆，而不是抽一个容纳所有场景的大组件：

- `useAdminList`：筛选、分页、取消旧请求、最新结果优先、错误与刷新。
- `AdminListShell` / `AdminDataTable`：工具栏、状态区、表格和分页。
- `useResourceUpload`：签名、上传、进度、失败重试和清理。
- 资源类型自己的Editor：音乐、GLB、场景和动作分别管理业务字段。

前后端共享明确的DTO和分页类型，逐步移除页面中的`any`；保留Nuxt UI，不引入第二套UI框架。

### A2 · Peer转发处理器耦合宠物默认形象、建档与设备列表增强

位置：`server/integrations/peer/handler.ts:101-137`。

通用代理根据硬编码path处理宠物创建前置校验、本地同步、设备列表装饰。新增一种设备或实体时，容易将更多业务继续堆入同一个函数。

建议保持已有endpoint白名单，把`beforeForward`、`afterSuccess`、`transformResponse`作为显式扩展点；领域逻辑放入pet/device服务。上游成功本地失败已有`upstreamApplied`提示，但应追加可重放的同步任务或outbox，避免长期只能人工修复。

### A3 · 本地账号、Peer账号和会话知识分散

证据是刷新接口修好后，设备告警仍留着相同映射错误。登录、密码登录、刷新还分别处理会话、刷新证明和Peer响应校验，后续容易分叉。

建议形成`IdentityService`、`SessionService`和纯函数账号映射；不要求微服务化。会话写入使用原子操作或可恢复流程，刷新增加同一proof的并发保护。当前多个刷新同时读到旧proof后会各自调用上游，遇到一次性刷新令牌轮换时仍有竞争；现有测试尚未验证这一点。

### A4 · 页面注册、权限和缓存规则缺少唯一来源

导航项在layout，标题与图标在useTabStore，页面权限又散落在后端与localStorage判断。新增页面需要同步多处。AGENTS.md也仍声称无测试、无迁移工具，与当前实现不符。

建议建立一份后台页面清单（路径、标题、图标、权限、缓存、分组）；后端权限仍独立可靠执行。更新项目文档并在CI运行现有check，避免新文件受`/tests`忽略规则影响而遗漏提交。

## 四、日志查询与可观测性

### L1 · P2：静默上游日志后，故障阶段没有完整保留

位置：`server/utils/peerBackend.ts:121-164`，`server/integrations/peer/handler.ts:110-113`，`server/plugins/logger.ts:39-57`。

代理传`quiet:true`后，网络错误不再打印上游诊断；处理器在await成功之后才填上游耗时/状态。超时、连接失败时，最终两条日志可能缺少上游路径、host、阶段和失败耗时。保留“两条日志”是合理需求，问题是诊断字段没有一起传回context。

建议：上游出口将安全错误码、host/path/stage/duration写入请求context，在最终返回日志一次打印；成功和失败使用同一字段定义。不要恢复多条重复正文日志。

### L2 · P2：429缺少可操作的限流原因，且多设备共用额度

位置：`server/middleware/rateLimit.ts:43-64`，`server/utils/requestLog.ts`。

同一IP下的OpenAPI默认接口共用60秒60次，多设备经同一后台上报会互相占额度。返回日志没有limit/count/window/retryAfter，也未设置Retry-After，用户看到的还是通用错误原因。

建议：保留粗粒度入口防护，在认证后按合作方、路由和设备增加业务限流；不同信任层分开计数。429附`RATE_LIMIT_EXCEEDED`、限制值、实际次数、剩余秒数；客户端不要立即重复提交。XFF只能来自受信代理，需确认nginx覆盖来访者自带的转发头。

### L3 · 调试正文与审计日志应分别定义

token明文是此前按用户排查要求临时开启，不能当作无意泄漏的回归。当前默认仍显示token且没有自动失效机制，应在排查结束后确认是否恢复，而非在本次审查中悄悄改变。

建议支持按路由、账号或设备开启有有效期的调试窗口；正常日志不含票据和完整个人资料；保持生产摘要与受控调试正文分流，并设置保留天数、访问权限和轮转。完整业务JSON可能很大，现有上游最大4MiB，持续全量记录会放大日志和内存开销。

当前请求日志还缺管理员actor、变更目标、操作类型与变更结果，不能替代安全审计流水。配置、积分、封禁、管理员权限修改应有独立审计事件，只存允许的差异和关联ID，不存密钥或完整密码字段。

参考：[OWASP日志指南](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html)。

### 建议的查询能力

保留北京时间前缀与一请求一返回；采集器解析前缀后按JSON字段索引。查询至少支持时间、requestId、route、HTTP状态、业务码、上游、管理员ID和设备ID（经授权/脱敏）。页面可输入requestId查看调用结果，并一键复制脱敏排查信息；不要提供可任意读取服务器文件路径的“日志接口”。

## 五、网络和部署边界

### N1 · P2：部署失败会直接停服，缺少自动回退

位置：`deploy.sh:108-140`。

先stop，再删除旧server/public，然后安装依赖并检查数据库版本。若迁移缺失、安装失败或健康检查失败，旧服务已经停止且旧产物被替换。脚本没有自动恢复上一个可运行版本。

建议：新产物进入独立release目录，先校验包/迁移/依赖，再切换current，失败恢复旧指向并重启旧版本。回退应用代码与回退数据库分别设计，不自动执行危险的降级SQL。

### N2 · P2：SSH主机校验关闭，应用以root运行且监听全部网卡

位置：`deploy.sh` 的 `StrictHostKeyChecking=no`、SSH_USER、PM2启动命令。

建议固定known_hosts指纹，使用专用部署账号与应用账号；Node绑定回环或应用私网接口，由nginx提供TLS和入口限额。是否已有防火墙阻止3000公网访问，本轮没有实际联网探测，不能据源码认定端口已经对外开放。

### N3 · 待线上核验项

- 云安全组/主机防火墙：只开放必要的80/443和受限SSH；MySQL/Redis不对公网开放。
- nginx：TLS、证书更新、受信代理头、body与连接限额；管理页面的CSP、frame-ancestors、nosniff与Referrer-Policy。
- Peer/AI出口：代码允许HTTP/HTTPS，生产公网必须验证实际走TLS；内部明文只能处于明确受控私网或隧道。
- OSS/CDN：桶公共读写策略、上传大小、可执行内容、签名有效期、跨域和访问日志。
- MySQL/Redis：最小权限账户、备份恢复、远程连接TLS及连接来源限制。

仓库未提供足够的nginx/防火墙/云权限证据，本轮未SSH登录或扫描线上，以上是验证清单，不是已经确认的漏洞。

## 六、建议实施次序

1. **先修明确风险与业务失败**：S1构建密钥、S2设备告警映射；分批升级依赖；核验上游统一密码边界。签名v2与调用方协调迁移，避免直接切开关造成全部回调失败。
2. **建立一套UI基线**：选用户/设备列表和音乐资源页作为样板；完成错误/空态、响应式、操作分级、权限只读、表单dirty保护。确认样板后推广到其余页面。
3. **抽取稳定业务边界**：列表与上传composable、页面注册清单、身份会话服务；拆分Peer扩展点，添加同步补偿。
4. **运维闭环**：429原因与分层限流、两条日志的失败诊断、调试窗口和管理员审计查询、可回退发布。

建议验收用真实运营任务：找一个用户并查积分；定位一台离线设备；审核帖子；上传并试听音乐；修改一条形象规则并预览；按requestId定位一次失败。每项覆盖成功、无权限、接口失败、重复提交与窄屏。现有测试绿灯不是这些交互已经验收的证据。
