## 尚需确认的发布条件

1. App 的短信设置密码入口及签名 v2 支持范围。可先封堵默认密码并保留短信登录，不必等待全部客户端升级。
2. Peer 的共享设备权限、固定密码登录入口与 token 撤销能力。不能把“可读设备列表”当成“拥有设备”。
3. AI 数量单位、精度、计费取整与稳定事件 ID。不能在安全修复中无声更改计费方式。
4. 实际 MySQL 版本、现有 schema、session time_zone 和部署代理配置。本次仅核对代码定义，未访问生产确认。
5. 历史缺失权益的核对与补偿政策。不得根据可能重复或缺失的历史流水机械补发。

以上是实施前或发布前的外部依赖，已在方案中说明；不是新的确认请求，也不阻塞其余独立修复。

## 防止过度改造

- 不拆微服务，不引入通用规则语言，不重写所有后台页面。
- 不把所有重复代码都抽象成通用 CRUD；先收敛已产生不一致的日期、发放、权限和事务。
- 不删除 GLB 快照，它是历史分配记录，不是无意义冗余。
- 不在每个请求中自动修 schema，不把外部网络调用放入数据库长事务。
- 不全量重置个人密码，不全表平移历史日期，不为测试绿灯删断言。
- 不把格式清理与账务/鉴权修复混成一个难以回退的大提交。

建议执行起点：A 建立可验证基线，同时推进 B 的默认密码拒绝与设备权限修复；D 的账务改造作为完整事务边界独立交付。E 的协议切换在调用方完成联调后进行。
