## Context

`t_pet` currently only supports create + list (`server/routes/sdkapi/pet/create.post.ts`, `list.get.ts`), inserts via raw `AUTO_INCREMENT`-style `result.insertId` instead of the project's Snowflake `generateId()`, and has no admin surface at all. There is no shared `server/utils/oss.ts` — every upload-sign route (`server/routes/sdkapi/upload/sign.post.ts`, `server/routes/api/admin/music/upload-sign.post.ts`, `server/routes/api/admin/sound/preset/upload-sign.post.ts`) duplicates its own `ali-oss` client + `signatureUrl` call, none of which currently allow GLB MIME types. Three separate auth surfaces already exist: `/sdkapi/**` (signature + `requireAuth` bearer token), `/api/admin/**` (global `admin-auth.ts` JWT middleware), `/openapi/**` (hardware/peer-backend signature, e.g. `server/routes/openapi/device-event/callback.post.ts`). "Current state" caching already has two precedents: append-only history (`t_device_event` + `sdkapi/device-event/list.get.ts`) and Redis-first/DB-fallback latest-value (`device:position:<mac>` in `sdkapi/device/position.get.ts`). See proposal.md for motivation and specs/ for behavior contracts.

## Goals / Non-Goals

**Goals:**
- Bring `t_pet` and its CRUD up to the project's own conventions (Snowflake id, soft delete, admin JWT, string-coerced BIGINTs) rather than inventing new ones.
- Reuse the existing OSS presign-and-direct-PUT pattern for all new binary assets (backgrounds, GLB models, GLB animations) instead of proxying uploads through the server.
- Model the hardware-action "current state" the same way `device:position` already does (Redis latest-value + DB durability), since that is closer to "poll for current state" than the append-only event-log pattern.
- Both hardware action codes and interaction types are true admin-manageable CRUD resources (create/list/update/delete), each seeded with initial rows (5 hardware codes, 3 interaction types) that admins can extend or remove as hardware capabilities and gameplay needs evolve — neither set is hardcoded or closed.
- Unify both interaction-triggered and hardware-reported activity into a single `t_pet_event` log so admins have one place to review pet history instead of two unrelated logs.

**Non-Goals:**
- Not implementing real-time push (WebSocket/MQTT) of hardware actions to the App — proposal explicitly says polling.
- Not handling GLB file validation/parsing server-side; the server only stores and signs URLs, never inspects 3D model contents.
- Not building a generic decay/scheduler background job in this change; decay is computed lazily at read/interaction time (see Decisions).

## Decisions

### 1. Extend `t_pet` in place; new tables for library resources, action state, and a unified event log
Add `satiety`, `mood`, `cleanliness` (TINYINT/SMALLINT 0-100), `background_id`, `model_id`, `stats_updated_at` (DATETIME) to `t_pet`, plus `updated_at` (currently missing). New tables: `t_pet_background`, `t_pet_model`, `t_pet_glb_action` (the standalone animation-resource library — id, name, glb_url, preview_url, enabled, deleted, created_at, updated_at), `t_pet_interaction_type` (full CRUD resource, seeded with 3 initial rows — feed/play/clean: code, name, icon, `glb_action_id` FK into `t_pet_glb_action` — nullable, admin-editable mapping, satiety/mood/cleanliness effect columns, enabled, deleted), `t_pet_hardware_action_type` (full CRUD resource, seeded with 5 initial rows: code, name, icon, `glb_action_id` FK into `t_pet_glb_action` — nullable, admin-editable mapping, enabled, deleted), `t_pet_event` (unified append-only log: `id`, `source` ENUM('interaction','hardware_action'), `pet_id` BIGINT NULL, `device_id` BIGINT NULL, `ref_type_id` BIGINT — points at the `t_pet_interaction_type.id` or `t_pet_hardware_action_type.id` involved, `occurred_at` DATETIME, `created_at` — mirrors `t_device_event`'s pattern but covers both trigger sources instead of one, for the admin event query page). All new tables use `id BIGINT PRIMARY KEY` populated by `generateId()`, `deleted TINYINT DEFAULT 0` (except `t_pet_event`, which is append-only and never soft-deleted), `created_at`/`updated_at DATETIME`.
- **Alternative considered**: a single generic `t_pet_resource` table with a `type` discriminator column for backgrounds/models/GLB actions/interactions. Rejected — the resource kinds have different required fields (models need thumbnail, interactions need stat-effect JSON + a GLB action reference, backgrounds need only an image, GLB actions need only a file + preview), so separate tables keep each admin CRUD route simple and match how `music` vs `sound preset` are already separate tables rather than one polymorphic table.
- **Alternative considered**: let `t_pet_interaction_type` and `t_pet_hardware_action_type` each store their own `glb_url` directly (the original design of this change, before feedback). Rejected — this conflates two different concepts: a hardware action code is a physical-state identifier the device reports, not an animation; an interaction type's animation should be swappable/reusable independent of the interaction's stat effects. Extracting `t_pet_glb_action` as the single place animation files live means the same GLB (e.g. a generic "sit" animation) can back both a hardware action code and an interaction type without duplicate uploads, and an admin can swap an animation everywhere it's used by editing one row.

### 2. Switch new `t_pet` writes to `generateId()`, backfill nothing
New create/update code paths use `generateId()` for all new rows (pets, backgrounds, models, interaction types, action log entries). Existing pet rows created via `insertId` keep their existing (smaller, numeric) ids — no backfill/migration of existing ids, since both id shapes coexist fine as opaque BIGINT strings on the wire.
- **Alternative considered**: migrate existing `t_pet.id` values to Snowflake ids. Rejected — churns foreign keys (`t_pet_fence.device_id` references, any App-cached ids) for no behavioral benefit.

### 3. Hardware action "current state" = Redis-first + DB event log, not just an event table; code is resolved to a GLB URL at read time, not at write time
`openapi/pet/action/report.post.ts` (signature-protected, same middleware as `device-event/callback.post.ts`) validates the reported value is a currently defined, non-deleted `t_pet_hardware_action_type.code` and writes only the **code** (plus timestamp) into Redis (`RedisKey.petAction(deviceId)`, TTL a few hours), and also appends a `{source: 'hardware_action', device_id, ref_type_id, occurred_at}` row to the unified `t_pet_event` table. Neither the Redis value nor the event row stores a GLB URL. `sdkapi/pet/[id]/action.get.ts` reads the code from Redis first (falling back to the latest matching `t_pet_event` row for that device if the Redis key is missing), then does a small lookup of `t_pet_hardware_action_type.glb_action_id` for that code, joins to `t_pet_glb_action` for the current URL, and returns `{code, reportedAt, glbUrl}`. This means re-mapping a code to a different animation (Decision in pet-hardware-action spec) takes effect immediately for every subsequent poll, with no need to touch Redis or the event log. `sdkapi/pet/[id]/interact.post.ts` (section 4 below) similarly appends a `{source: 'interaction', pet_id, ref_type_id, occurred_at}` row to the same `t_pet_event` table on every successful interaction.
- **Alternative considered**: rely solely on an append-only table for "current state" (i.e., "current" = latest row via `ORDER BY created_at DESC LIMIT 1`). Rejected as the sole mechanism — polling is expected to be frequent (animation sync), and hitting MySQL with `ORDER BY ... LIMIT 1` per poll for every online device is unnecessary load compared to a Redis GET; the table is kept anyway for admin history/audit, so this is additive, not a replacement.
- **Alternative considered**: resolve the code to a GLB URL once at report time and store the resolved URL in Redis/the event row. Rejected — this would freeze the animation mapping at report time, so changing a code's mapping in the admin UI would not affect a device's already-cached "current action" until its next physical state change triggers a fresh report; resolving at read time keeps re-mapping instantly effective.
- **Alternative considered**: keep a separate `t_pet_hardware_action_log` (hardware-only) alongside a separate interaction log. Rejected after feedback — admins want one unified place to review both interaction and hardware activity per pet, so a single `t_pet_event` table with a `source` discriminator serves both without an admin having to cross-reference two pages.

### 4. Decay computed lazily, not via a background cron job
`t_pet.stats_updated_at` stores the last time stats were written. Every read (`GET /sdkapi/pet/:id/status`) or interaction computes `elapsed = now - stats_updated_at`, applies `decay = elapsed_minutes * configured_rate` per stat (floored at 0), and — only on interaction — persists the decayed-then-adjusted values with a fresh `stats_updated_at`. Plain status reads return the computed value without writing (avoids a write on every poll).
- **Alternative considered**: a scheduled job (cron/PM2 cron) that ticks all pets' stats down periodically. Rejected — this repo has no existing job scheduler/worker process (deployment is a single PM2 Nitro process per AGENTS.md), and lazy computation gives identical externally-observable results without adding a new always-on process or missed-tick edge cases.

### 5. OSS upload-sign gains a `.glb` MIME entry; no new shared util extracted
Each existing upload-sign route (`admin/music`, `admin/sound/preset`) hand-rolls its own MIME→extension map inline; the new `admin/pet-resources/upload-sign.post.ts` (serving backgrounds + models + GLB action resources from one endpoint, parameterized by `folder` — `pet-background`|`pet-model`|`pet-glb-action`) follows the same inline pattern and adds `'model/gltf-binary': 'glb'` (and accepts a raw `.glb` extension hint from the client since browsers often report GLB uploads as `application/octet-stream`). Note interaction types and hardware action codes never call this endpoint directly for a GLB — they only ever pick an existing `t_pet_glb_action` row by id via their own CRUD routes; all GLB uploads flow through this one endpoint into the `t_pet_glb_action` library. Introducing a shared `server/utils/oss.ts` is out of scope for this change — it would touch the three existing unrelated upload-sign routes and is a pure refactor with no behavior change, which AGENTS.md-style conventions in this repo don't require alongside a feature change.
- **Alternative considered**: extract a shared OSS util now. Deferred — bundling an unrelated refactor into this feature change increases review surface without changing any spec; can be proposed separately later if duplication becomes painful.

### 6. Three new admin pages under `app/pages/admin/virtual-pet/`
`app/pages/admin/pets/index.vue` (pet profile CRUD, flat under `pets/` matching the `users/`, `devices/` convention) is separate from the virtual-pet resource pages, since pet-profile management is conceptually distinct from game-resource configuration. The proposal-mentioned pages become `app/pages/admin/virtual-pet/scenes.vue` (tabs or sections for backgrounds / models / GLB action library / interaction types — four true create/delete CRUD lists in one page, avoiding page sprawl for what the proposal frames as one "环境编辑" page; the GLB action library tab is where all animation files actually get uploaded, and the interaction type tab's create/edit form picks one via a dropdown of existing GLB action resources rather than uploading its own file), `app/pages/admin/virtual-pet/actions.vue` (hardware action code CRUD list, matching the proposal's "宠物硬件动作管理" page — add/edit/delete codes, plus a dropdown per row to pick/clear the mapped GLB action resource), and `app/pages/admin/virtual-pet/events.vue` (the unified pet event query page: filter bar for pet/device/source-type/date-range, backed by `GET /api/admin/pet-events`, replacing what would otherwise be a hardware-only "recent report monitor" — this single page covers both interaction and hardware-action history). All three follow the existing hand-rolled-modal + native `<table>`/grid list pattern (`device-events.vue`, `music/index.vue`) rather than introducing `UTable`/`UModal`, to stay visually and behaviorally consistent with the rest of the admin console.

## Risks / Trade-offs

- [Risk] Redis is not durable; if `petAction` key evicts and no report has landed recently, polling falls back to the DB log, which is one extra query on cache miss. → Mitigation: TTL set generously (a few hours) relative to expected report frequency; DB fallback keeps correctness even on total Redis flush.
- [Risk] Lazy decay computation means two pets read at different times from the same "tick" can show slightly different decay if stat-effect config changes mid-flight (config changes apply going forward only from each pet's own last-updated timestamp). → Mitigation: acceptable for a cosmetic game stat; not a financial or safety-critical value.
- [Risk] GLB files are unvalidated by the server (no size/content check beyond OSS's own limits). A malicious admin could upload an oversized or malformed GLB. → Mitigation: admin-only surface (already JWT-gated), consistent with how audio/image uploads are handled today; out of scope to add 3D file validation.
- [Risk] The initial hardware action codes and interaction types are seeded via `init.sql`/one-time inserts; if a fresh environment forgets to seed them, `sdkapi/pet/action.get.ts`, `sdkapi/pet/interact.post.ts`, and both admin CRUD pages start with an empty list. → Mitigation: seed rows for both ship in `sql/init.sql` itself (not a separate migration step), matching how this repo already manages schema (single file, run manually); since both are now full CRUD resources, an admin can also re-create rows manually if a seed is missed.
- [Risk] Because hardware action codes and interaction types are admin-deletable, deleting one that's still referenced by devices/pets in flight could cause hardware reports or interactions to suddenly be rejected as "unknown code/type". → Mitigation: this mirrors how deleting a `t_pet_glb_action` still referenced elsewhere is handled (soft-delete, referencing entities resolve to "no match" rather than erroring); acceptable since this is an admin-operated console, not an uncontrolled multi-tenant surface.

## Migration Plan

1. Add new columns to `t_pet` and create the new tables (`t_pet_background`, `t_pet_model`, `t_pet_glb_action`, `t_pet_interaction_type`, `t_pet_hardware_action_type`, `t_pet_event`) in `sql/init.sql`; apply manually against the dev/staging DB per existing convention (no migration tool in this repo), then production during the next deploy window.
2. Seed `t_pet_hardware_action_type` with 5 initial rows (lying/eating/sitting/walking/standing) and `t_pet_interaction_type` with 3 initial rows (feed/play/clean) as part of the same SQL script; both seeds ship with `glb_action_id = NULL` until an admin maps them. These are starting data, not a hard limit — admins can add/remove rows afterward via their respective admin CRUD pages.
3. Ship server routes and admin pages together (single PM2 process, single deploy via `./deploy.sh`); no phased rollout needed since these are net-new endpoints/pages with no callers yet.
4. Rollback: since all changes are additive (new columns with defaults, new tables, new routes/pages), reverting the deploy is sufficient; no destructive schema changes are introduced, so no down-migration is required.
